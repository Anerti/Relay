# AGENTS.md

Relay is a Spring Boot REST API (users, JWT auth, direct messages, AI-agent conversations, per-account host/event logs). Most of it is still specified, not built: `docs/api/api.yaml` is the contract, and only `GET /syn`, `POST /auth/register`, `POST /auth/login`, `GET /auth/verify/{token}`, `POST /auth/mfa/confirm/register/{token}`, `POST /auth/mfa/confirm/login/{token}`, `GET /users`, `GET /users/{userId}`, `PATCH /users/{userId}`, `DELETE /users/{userId}`, `GET /messages/users/{userId}`, `POST /messages/users/{userId}` and `DELETE /messages/{messageId}` are implemented so far.

## Stack

- Java 27 (Gradle toolchain), Spring Boot 4.1.2, Gradle wrapper
- Spring Web MVC, Security, Data JPA, Data Redis, Flyway
- PostgreSQL (schema `relay_app`), Redis
- jjwt 0.12 (HMAC), Argon2 password hashing (Bouncy Castle)
- Jackson 3 (`tools.jackson.*`), Lombok
- Spring Mail with Thymeleaf HTML templates (`src/main/resources/templates/mail`); server-rendered pages in `templates/auth`

## Commands

```sh
./gradlew bootRun     # run locally (needs .env, Postgres, Redis)
./gradlew test        # tests; needs Docker (Testcontainers)
./gradlew check       # tests + JaCoCo gate: 85% instruction coverage, fails the build below it
```

## Configuration

`src/main/resources/application.properties` imports `.env` (gitignored, never commit it) as properties. Keys it must provide:

- `spring.datasource.url`, `spring.datasource.username`, `spring.datasource.password`
- `app.jwt.secret`: Base64, at least 256 bits once decoded
- `app.cors.allowed-origins`: comma-separated
- `app.geoip.url`: base URL of the MaxMind-GeoIp service (`GET /geoip?ip=`). `app.geoip.timeout` (1s, connect and read) is set in `application.properties`.
- `spring.data.redis.host`, `spring.data.redis.port`, `spring.data.redis.username`, `spring.data.redis.password`. Use these, not `spring.data.redis.url`: when a URL is set, Spring reads credentials only from the URL and ignores the username and password keys. Add `spring.data.redis.ssl.enabled=true` if the provider requires TLS. `spring.data.redis.timeout` (500ms) is set in `application.properties`.
- `spring.jpa.hibernate.ddl-auto=validate`, `spring.jpa.open-in-view=false`
- `spring.mail.username` (Gmail address, also the sender), `spring.mail.password` (Gmail App Password, needs 2-Step Verification; the account password is rejected). Host, port and STARTTLS are in `application.properties`.
- `app.base-url`: public URL that emailed links point to (`http://localhost:8080` locally)

`server.forward-headers-strategy=none` is set in `application.properties`: Relay is not deployed behind a proxy, so `X-Forwarded-*` headers are ignored and the client IP is the address that opened the connection.

Tests get Postgres, Redis, a Mailpit SMTP server, a stub GeoIP server and a random JWT secret from `TestcontainersConfig`; `src/test/resources/application.properties` holds the rest. Read delivered mail through Mailpit's REST API at `mailpitApiUrl()`.

## Layout (`src/main/java/com/techindna/relay`)

| Package | Holds |
|---|---|
| `controller` | REST controllers |
| `dto` | Request and response bodies named after their spec schemas (`RegisterInput`, `MessageBody`) |
| `entity` | Domain records returned by the API (`User`) and enums; `entity/email` holds `EmailDetails` and `EmailTemplate` |
| `service` | Business logic and transactions: `UserService`, `MessageService`, `auth`, `mail`, `redis`, `mapper`, `event` (`HostEventService`: hosts and event logs), `event/auth` (emails sent by auth flows), `enums` |
| `repository` | Repositories |
| `repository/model` | JPA entities, prefixed `J` (`JUser`) |
| `exception`, `exception/http` | `ErrorBody`, `GlobalExceptionHandler`, one exception per HTTP status |
| `validator` | `DataValidator`: input normalization and validation; `AuthValidator`, `UserValidator` and `MessageValidator` compose it per request body |
| `security`, `security/jwt` | Filter chain, JWT issue/verify, ABAC and RBAC rules, client IP resolution |
| `config` | CORS, GeoIP `RestTemplate` |

## Conventions

- **Schema changes go through Flyway** (`src/main/resources/db/migration/V<n>__<name>.sql`), never `ddl-auto`. Hibernate only validates. Never edit an applied migration; add a new one.
- **GeoIP** comes from the separate MaxMind-GeoIp service over HTTP: `GeoIpService` calls `GET <app.geoip.url>/geoip?ip=<ip>` with the `RestTemplate` from `GeoIpClientConfig` and returns `null` on any `RestClientException` (down, timeout, 4xx/5xx), logged. Relay has no GeoIP endpoint or data of its own. The test stub answers `203.0.113.42` with Lisbon data (without `ipAddress`, so the email must show the request's IP) and any other IP with 400.
- **Postgres enums** are named types in `relay_app`, mapped with `@JdbcTypeCode(SqlTypes.NAMED_ENUM)`. Adding a Java enum value needs a migration too. Java and DB values are upper case; JSON writes them lower case (`spring.jackson.datatype.enum.write-enums-to-lowercase=true`, in both `application.properties` files), matching the spec.
- **Entities vs domain**: JPA entities (`J*`) stay in `repository/model`; controllers return `entity` records, never JPA entities (`JUser` carries the password hash). `JUser` is `@DynamicUpdate`, so an UPDATE writes only the changed columns and concurrent updates of different fields do not overwrite each other.
- **Errors**: throw an `exception/http` exception; `GlobalExceptionHandler` turns it into `ErrorBody` JSON, always with `Content-Type: application/json` so it is written whatever the `Accept` header says. Filters and security handlers write errors with `ErrorBody.send(...)`. Wrong method is 405 with `Allow`, an `Accept` that excludes the response type is 406. JSON endpoints with side effects declare `produces = MediaType.APPLICATION_JSON_VALUE` so the 406 comes before the handler runs. Unknown exceptions become a generic 500, logged.
- **Validation**: use `DataValidator`. Semantic problems are 422 (`UnprocessableContentException`), malformed requests and bad pagination are 400. Lengths count Unicode code points, matching the spec's `maxLength` and Postgres `VARCHAR(n)`. Username and email are trimmed and lower-cased before checks and storage; uniqueness is case-insensitive in the DB.
- **Auth**: stateless JWT in `Authorization: Bearer`. Claims: `sub` = user id, `role` (becomes `ROLE_<role>`), `ip_address`. `ABACRules.authorizeIpAddress` rejects a token used from a different IP with 403. A token without `sub` is treated as invalid (401). Only `GET /syn`, `/auth/register` and `/auth/login` (every method, so wrong ones get 405 instead of 401), `GET /auth/verify/*`, `POST /auth/mfa/confirm/register/*`, `POST /auth/mfa/confirm/login/*` and error dispatches are public. `SecurityConfig` denies by default: each authenticated endpoint is listed there with its method (`GET /users/*`, `PATCH /users/*`, `DELETE /users/*`, `GET /messages/users/*`, `POST /messages/users/*`, `DELETE /messages/*`, and `GET /users` with `hasRole("SUPERUSER")`), and anything unlisted, including a trailing slash and a wrong method such as `POST /syn` or `PUT /users/{userId}`, is blocked before MVC with 401 `Authentication required.` without a token or 403 `Insufficient privileges.` with one. A wildcard matcher also accepts an empty last segment (`/users/`, `/auth/verify/`); those requests reach MVC and get 404 `Resource not found` (`NoResourceFoundException`). Add every new endpoint to `SecurityConfig`.
- **Registration and verification mail**: `POST /auth/register` validates the whole body before hashing, saves the user with `verified=false`, stores a 15-minute token in Redis (`auth:verification:<uuid>` = `<VerificationFlow>:<userId>`), and sends the email synchronously inside the transaction. On any mail failure, delete the token and rethrow so the user insert rolls back and the client gets a 500. Duplicates are told apart by constraint name (`user_username_lower_key`, `user_email_lower_key`), never by the DB message, which embeds user input. Links are `app.base-url` + `/auth/verify/<token>`. The email shows the client IP's GeoIP details (continent, country, city, timezone, coordinates, accuracy radius, AS organization) from `GeoIpService`; a failed lookup is logged and those rows show `N/A`, it never fails the registration.
- **Login**: `POST /auth/login` validates either username or email plus the password (both together is 422), then rejects `LOCKED` accounts, unverified accounts and banned hosts; `INACTIVE` accounts can still request a login link. Wrong credentials use one 401 message whether the account exists or not, and an unknown username/email still hashes the given password with Argon2 so timing does not reveal the account. An unknown username/email is not logged; every failed attempt on a known account gets a persisted `[LOGIN]` event on the request host — `MEDIUM` `[LOGIN FAILED]: invalid credentials` for a wrong password, or `MEDIUM` `[LOGIN FAILED]: account locked`, `[LOGIN FAILED]: account not verified`, `[LOGIN FAILED]: host banned` for blocked attempts. The method uses `@Transactional(noRollbackFor = {ForbiddenException.class, UnauthorizedException.class})` so those audit writes commit while the 401/403 is returned. On success it records the caller's host and an `INFO` `[LOGIN]: Verification link requested` event, stores a 15-minute `LOGIN` token in Redis and sends the login verification email synchronously inside the transaction; a mail failure deletes the token and rolls everything back.
- **Verification page**: `GET /auth/verify/{token}` renders `templates/auth/auth-redirection.html`, a form that POSTs to `/auth/mfa/confirm/register/{token}` or `/auth/mfa/confirm/login/{token}` depending on the token's flow. `VerificationService.confirmationFlow` reads the flow from Redis through `VerificationTokenService.findFlow` without consuming the token; unknown or malformed tokens, and Redis failures (logged), default to the registration target. It does not touch the account, and the confirm endpoint answers 401. It sends `Cache-Control: no-store` and `Referrer-Policy: no-referrer` because the token is in the URL.
- **Registration confirmation**: `POST /auth/mfa/confirm/register/{token}` (`VerificationService`) consumes the token atomically with `VerificationTokenService.consume` (Redis `GETDEL`), so it is gone even when the request then fails. A missing, malformed or non-`REGISTER` token, or a deleted user, is 401 `Invalid or expired token`. Otherwise it sets `verified=true`, records the host and an `INFO` "Account verified" event, and returns a JWT bound to the caller's IP plus the `User` record.
- **Login confirmation**: `POST /auth/mfa/confirm/login/{token}` also consumes the token first, so it cannot be retried. A missing, malformed or non-`LOGIN` token, or a deleted user, is 401 `Invalid or expired token` and is not logged; a non-active (locked or inactive) or unverified account, or a banned host, is 403 and records the host plus a `MEDIUM` `[LOGIN FAILED]: account locked or inactive`, `[LOGIN FAILED]: account not verified` or `[LOGIN FAILED]: host banned` event that commits despite the exception. Otherwise it records the host and an `INFO` `[LOGIN]: Account signed in` event and returns a JWT bound to the caller's IP plus the `User` record.
- **Hosts and event logs**: `HostEventService.recordHost` upserts the caller's host for (user, client IP) with `INSERT ... ON CONFLICT DO UPDATE` on `last_seen_at`, so concurrent first requests from one IP do not hit the unique key; `ClientDataConfig.ipAddress` strips an IPv6 zone id (`fe80::1%1`), which Postgres `inet` rejects. `logEvent` writes an event log with the user agent (`Unknown` if missing, cut to 512 chars). Call both inside the flow's transaction so they roll back with it, unless an exception is explicitly marked `noRollbackFor`. `POST /auth/register` records the host and an `INFO` `[REGISTRATION]: Account registered` event before sending the email; `POST /auth/login` records the host and `[LOGIN]` events, and its confirmation records an `INFO` `[LOGIN]: Account signed in` event; `POST /messages/users/{userId}` records an `INFO` `[MESSAGE]: Message sent to <receiverId>` event, and a `MEDIUM` `[MESSAGE]: Send failed due to locked account` or `[MESSAGE]: Send failed due to banned host` event when the caller is blocked; `GET /messages/users/{userId}` records an `INFO` `[MESSAGE]: Conversation read with <userId>` event, and a `MEDIUM` `[MESSAGE]: View failed due to locked account` or `[MESSAGE]: View failed due to banned host` event when the caller is blocked; `DELETE /messages/{messageId}` records an `INFO` `[MESSAGE]: Message <messageId> deleted` event, and a `MEDIUM` `[MESSAGE]: Delete failed due to locked account` or `[MESSAGE]: Delete failed due to banned host` event when the caller is blocked; `PATCH /users/{userId}` records an `INFO` `[PROFILE]: Profile data changed` event when the username, first name or last name changes, and a `MEDIUM` `[PROFILE]: Update failed due to unverified account` event when an unverified account tries.
- **Account access**: `RBACRules.authorize` lets a superuser reach a guest account or their own and a guest only their own; anything else is 403 `Cannot access this resource.` (a token without a role is 403 too). `GET /users/{userId}` (`UserService.getUser`) looks the user up first, so an unknown id is 404 `User not found` before the access check; a malformed id is 400.
- **Profile update**: `PATCH /users/{userId}` (`UserService.updateUser`) validates the body with `UserValidator` first (each field optional; normalized like registration, then length and format, 422), then checks ownership before any lookup: only the owner may update, whatever the role, so a `userId` other than the token's `sub` is 403 `Cannot access this resource.` (`RBACRules.requireOwner`). The user is then looked up, and a missing one is 404 `User not found`; an unverified account is 403 `Verify your email address before updating your profile.` and records the host plus a `MEDIUM` `[PROFILE]: Update failed due to unverified account` event, which commits despite the exception (`@Transactional(noRollbackFor = ForbiddenException.class)`; the entity is not modified before that check). Locked and inactive accounts can still update. Omitted or null fields are left unchanged. The mapping declares `consumes = application/json`, so `application/merge-patch+json` is 415. `saveAndFlush` surfaces a unique violation (root `SQLException` with SQLState `23505`) as 409 `Cannot use this username`; the username is the only unique column the update can change. When at least one field actually changes (a new value differing from the stored one after normalization), it records the host and an `INFO` `[PROFILE]: Profile data changed` event after the save; an empty body or identical values record nothing.
- **Account deletion**: `DELETE /users/{userId}` (`UserService.deleteUser`) checks ownership before any lookup, like `PATCH /users/{userId}`: only the owner may delete, whatever the role, so a `userId` other than the token's `sub` is 403 `Cannot access this resource.` (`RBACRules.requireOwner`), and a token without a role can still delete its own account. The user is then looked up (404 `User not found` when the caller's own account is gone; malformed id 400). It deletes and flushes the row, so a DB failure surfaces before any email, then sends the `account-deletion-notification` email synchronously inside the transaction through `AccountDeletionNotificationService` (`service/event`) and answers 204. The email shows the request's IP and user agent. A `MailException` becomes 500 `Failed to send account-deletion notification email` (`InternalServerErrorException`) and rolls the deletion back. Hosts and event logs survive with `user_id` set to null (`ON DELETE SET NULL`); no event is recorded for the deletion.
- **User list**: `GET /users` (`UserService.listUsers`) is superuser-only in `SecurityConfig`, so a guest or a token without a role gets 403 `Insufficient privileges.` before MVC. It validates `search` (422) and `page`/`size` (400 `Invalid pagination parameters`, also when the page would start past item `Integer.MAX_VALUE`; a non-integer is 400 `Invalid parameter: page`), then pages with `PageRequest` sorted by `createdAt` then `id` (`order=desc` reverses, anything else is ascending). `role=superuser` lists superusers, any other value guests. The search is a case-insensitive literal substring match with JPQL `LOCATE` on the lower-cased username, first name, last name and email; `UserService` lower-cases the term, and `LOCATE` treats `_`, `%` and `\` literally (`%` and `\` never reach the query anyway because `validateSearchString` rejects them). A missing or blank `search` is passed as `null` and the query's `:search IS NULL` branch lists every account of the role. The body is `PageResponse<User>` (`data` + `Meta`); `data` is `null`, not `[]`, when no account matches.
- **Sending messages**: `POST /messages/users/{userId}` (`MessageService.sendMessage`) validates `content` with `MessageValidator` first (required and not blank, at most 4000 code points, 422; stored as sent, never trimmed). It then looks the caller up by the token's `sub` (gone is 404 `User not found`) and the receiver with `findByIdAndVerifiedTrue` (unknown or unverified is 404 `User not found`; locked and inactive receivers still get messages, and the caller may message themselves). It records the caller's host, then rejects a `LOCKED` caller (403 `This account is locked and cannot send messages.`) and a host `BANNED` for the caller's account (403 `Host <ip> is banned from accessing this account`), each with a `MEDIUM` `[MESSAGE]: Send failed due to locked account` or `[MESSAGE]: Send failed due to banned host` event that commits despite the exception (`@Transactional(noRollbackFor = ForbiddenException.class)`); `INACTIVE` callers can still send. `JMessage.senderId` is a plain `UUID` column; `saveAndFlush` runs inside a `try`, and a foreign-key violation (root `SQLException` with SQLState `23503`, the receiver deleted after the lookup) becomes 404 `User not found`. Any role, or none, may send. It saves a `JMessage` (`issuer=HUMAN`, `replyTo` null), records an `INFO` `[MESSAGE]: Message sent to <receiverId>` event, and answers 201 with the `Message` record. The mapping declares `consumes` and `produces` JSON (415, 406 before the handler). Validation failures and 404s record nothing. `message.sender_id` and `receiver_id` are `ON DELETE SET NULL` and indexed (`V3__message.sql`: `receiver_id`, and `(sender_id, receiver_id, created_at)`, which also covers `sender_id`), so messages outlive deleted accounts with a null id.
- **Listing messages**: `GET /messages/users/{userId}` (`MessageService.listMessages`) validates `page`/`size` first like `GET /users` (400 `Invalid pagination parameters`, non-integer 400 `Invalid parameter: page`, nothing recorded), then looks the caller up by the token's `sub` (gone is 404 `User not found`, nothing recorded). It records the caller's host, then rejects a `LOCKED` caller (403 `This account is locked and cannot view messages.`) and a host `BANNED` for the caller's account (403 `Host <ip> is banned from accessing this account`), each with a `MEDIUM` `[MESSAGE]: View failed due to locked account` or `[MESSAGE]: View failed due to banned host` event that commits despite the exception (`@Transactional(noRollbackFor = ForbiddenException.class)`; the check is shared with sending through `assertAllowed`); `INACTIVE` callers can still list. It then returns a `PageResponse<Message>` of the messages exchanged between the caller and `userId` in either direction (`MessageRepository.findConversation`, a `Page` query), excluding rows with `deleted_at` set, sorted by `createdAt` then `id` (`order=desc` reverses, anything else is ascending). `data` is `null` when the page is empty, like `GET /users`. The other user is not looked up: an unknown user or no shared messages give `data: null`; the caller's own id lists messages sent to themselves. Rows whose other party was deleted (null id) are not returned. Any role, or none, may list. It records an `INFO` `[MESSAGE]: Conversation read with <userId>` event. The mapping declares `produces` JSON, so a non-JSON `Accept` is 406 before anything is recorded. A malformed id is 400. The `(sender_id, receiver_id, created_at)` index in `V3__message.sql` serves both directions of the conversation query.
- **Deleting messages**: `DELETE /messages/{messageId}` (`MessageService.deleteMessage`) looks the caller up by the token's `sub` (gone is 404 `User not found`) and the message with `findByIdAndSenderIdAndDeletedAtIsNull` (unknown, sent by someone else, received by the caller or already deleted is 404 `Message not found`, so a second delete is 404 and other users' messages are not revealed; a superuser cannot delete others' messages). It records the caller's host and runs the shared `assertAllowed` check with `"Delete"` (403 `This account is locked and cannot delete messages.` or `Host <ip> is banned from accessing this account`, each with a committed `MEDIUM` event; `INACTIVE` callers can still delete). It soft-deletes: sets `deletedAt` to now and `saveAndFlush`es, keeping the row (content and `updatedAt` untouched), records an `INFO` `[MESSAGE]: Message <messageId> deleted` event and answers 204 with no body. A message whose receiver was deleted can still be deleted. Any role, or none, may delete. The mapping has no `produces` (no body), so any `Accept` works. A malformed id is 400. 404s record nothing.
